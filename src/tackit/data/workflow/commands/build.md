1. ORDER — build the UNCERTAIN / load-bearing piece FIRST and PROVE it before building on it (unverified work must not cross a boundary; a piece built on an unproven one takes the stack down). 2. TDD EACH INCREMENT — RED before GREEN.
   - Before writing code, NAME the slice rule each new behavior implements. A behavior no rule covers (a new lockout, a new message, new UI text) is a question for me: ask, don't build.
   - Write the failing test, watch it fail for the RIGHT reason, then the implementation, then GREEN. The RED run covers test-audit's Pass 0 for a NEW single-target test only. A test that loops over a set (authz sweeps, registry/guard scans, golden key-sets) must ALSO assert the set is non-empty and contains the real target, proven with one mutant (break one real member → RED). A test the change makes vacuous (it asserts on data or text that no longer exists) is a REWRITE — the firm-up impact sweep should have listed it.
     - RUNNING PLANTED MUTANTS: give each mutant its own copy of the source and tests in a fresh, uniquely named scratch directory (create it new; never clear an existing one), point the interpreter at that copy and check the imported code resolves into it (Python: PYTHONPATH to the copy's src), give each run its own test temp root and turn off shared caches (pytest: `--basetemp` set to a fresh directory named for the copy, on a RAM disk such as `/dev/shm` when the machine has one, because test file I/O can outweigh the tests themselves; and `-p no:cacheprovider`), and put one break in each copy, never several (grouped breaks hide which break failed which test). Launch every independent mutant at once, up to the machine's core count; run them one after another only when one mutant's result decides the next. When the test runner itself runs in parallel (pytest-xdist's `-n`), the concurrent mutants share one worker budget, the core count minus a few: pass each run `-n` equal to that budget divided by the number of concurrent mutants, at least 1 and at most the worker count the project's CLAUDE.md names, because a worker count in the project's test config is otherwise multiplied by every copy. A sweep question (which existing tests pin this behavior?) runs the full suite per mutant, because a test that builds its target set at runtime escapes a grep; proving one new test can fail runs that test's own file. Report per mutant what was broken and the failing test ids, or "0 failed": no test pins it, so the plan needs a new pin.
   - A UI / API gate is backend-enforced AND direct-API tested on EVERY write path to the gated state (FE-disabled ≠ backend-open).

2a. TEST-AUDIT — MANDATORY on every non-mechanical increment, run in-session; scope, exemption and routing are defined once in the `test-audit` skill ("When this audit is required"). Each finding is a FIX (real bug → change the code, resolve first) or a TEST (pin correct behavior). The increment's report carries the one `test-audit:` line that skill defines.

3. TEST CADENCE — RUN THE LEVEL EACH INCREMENT'S DIFF REACHES, NO HIGHER AND NO LOWER (the project's CLAUDE.md says what each level runs and what counts as "shared").
   - At each commit find the HIGHEST level the diff reaches and run that, once: (1) only new or changed test files → those files + every test file that imports a changed module (names-only search) + any repo-wide guard test (one that scans all files); (2) anything other tests depend on (app code, shared fixtures / conftest / factories, a helper other tests import, config or data that feeds prompts or schemas, migrations, requirements) → the full FAST (unit) suite; (3) app code, a migration / schema change, shared fixtures or a shared contract → also the full SLOW (integration) suite. A diff you cannot place → the higher level. Never re-run a suite no diff has touched since its last green run.
   - Unit is MANDATORY on any prompt / LLM-call change (the slow suite misses the prompt-governance guards).
   - Also run the full SLOW suite ONCE to prove a genuinely-uncertain load-bearing task that has dependents before building on it (step 1), and at the END of the meta's build, BEFORE any billed eval (with 3a). Rebuild the test image FIRST after any app-code / migration change when tests run against a built image — a stale image is a SILENT false pass/fail.
   - Run the LOCAL DEPLOY GATE (the e2e run against the deployed build) after any migration, constraint or fixture-affecting change — not only at the end; a new constraint breaks fixture replay that the integration suite never exercises.
   - Committed increments make an end-suite red git-bisectable.
