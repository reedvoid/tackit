⛔ DIAGNOSE, not fix. You reproduce the failure, PROVE its root cause with first-hand evidence, and WRITE that into the meta body — but you change NO product code and propose NO fix (that is /firmup → /graduate). ⭐ THE IRON LAW: **NO FIXES WITHOUT ROOT-CAUSE INVESTIGATION FIRST — a symptom fix is failure.** The deliverable is NOT "I understand it"; it is a DETERMINISTIC repro + a cause that BEATS EVERY RIVAL candidate on evidence. Read-only on product code; the only things you may write are the repro test and the meta body.

Target bug meta (+ any emphasis): $ARGUMENTS

1. READ — the meta, its linked neighbors, and the ERROR ITSELF, in full. Read the stack trace / log to the end (line numbers, paths, codes often carry the answer — don't skip past them). Then BUILD A READING LIST of the real code path and read each item IN FULL, first-hand — never a ±20-line window (a window confirms a `file:line`; it does not teach the flow). Every factual claim you will write carries `file:line` or the word UNVERIFIED — no third option; a universal quantifier (all/only/none) obliges an ENUMERATED check.

2. CHARACTERIZE THE SYMPTOM, then ENUMERATE A DIFFERENTIAL — the anti-fixation core. Write the symptom as a pure OBSERVATION, no cause in it. Then list SEVERAL candidate causes and keep them ALL live — at minimum the standing splits: a recent change **causes** it vs merely **exposes** a latent bug (⭐ CHECK RECENT CHANGES — git diff / new commits / config); the **code** is wrong vs the **check/test** is wrong (⭐ a failure is a DISAGREEMENT — it indicts BOTH sides equally; find the AUTHORITY — spec, design fact, real behavior — before blaming either); the cause is HERE vs UPSTREAM. ⛔ Do NOT collapse to one hypothesis here — a single opening hypothesis IS confirmation bias. Form a single hypothesis only AFTER the evidence has narrowed (step 4); hold the set until then.

3. REPRODUCE before theorizing — deterministic, $0, real entry point. Trigger the symptom reliably from a REACHABLE state via the real API / CLI / handler — NEVER a raw-SQL-fabricated state (it manufactures phantom bugs over states the app can't produce), and NEVER a billed run when the failing inputs already sit in the DB / logs. This repro IS the Phase-4 failing test, produced NOW as the proof — a trace is not a repro. ⭐ NOT reproducible → GATHER MORE DATA, do not guess (95% of "no root cause" is incomplete investigation, not a ghost).

4. DISCRIMINATE down to one — evidence at each boundary, eliminate candidates. For a multi-component path (parse → validate → query), log what data ENTERS and EXITS each boundary and find WHERE it breaks BEFORE asking WHY (add temporary instrumentation, run once, read the evidence). ⭐ TRACE THE BAD VALUE BACKWARD to its origin: from the line that fails, ask what called it and with what value, then what called THAT, until you reach where the bad value was made — that origin is the cause (the fix belongs at the source, not the symptom). When reading alone can't follow it, log the value plus a stack trace just BEFORE the failing operation and run once; when a stray state appears during a test run and no test is known to make it, run the tests one at a time until the first one that produces it. Find a WORKING sibling and list EVERY difference vs the broken one, however small ("that can't matter" is where the bug hides). Each evidence hop must ELIMINATE or CONFIRM a candidate (`file:line` or UNVERIFIED) — adversarially seek the evidence that would DISPROVE your leader; if two survivors have no discriminating test, you are NOT done. Root cause = the last candidate standing, proven to POSITIVELY beat the rest — never merely "consistent with."

5. FOLD THE PROVEN CAUSE INTO THE META — edit the meta body (it is the diagnostic ORIGIN; the eventual DECISION goes to a slice later via /graduate, never here). Write: CONFIRMED root cause (`file:line`) · the KILLED candidates + why each died (so no one revives them) · the $0 REPRO recipe · SYMPTOM vs BLAST-RADIUS (the one cause, and everything else it breaks) · the CAUSE-vs-EXPOSURE verdict · and leave the FIX DECISION explicitly OPEN (that is /firmup's to settle). If a LINKED task/spec is implicated (e.g. a recent change is the cause), flag it and wire/keep the link so the cascade carries it. ⭐ If diagnosis shows it is NOT a bug — an unreachable state, or a stale/LYING test asserting a state the app can't produce — say so and ROUTE it (wont_do / fix the test); never manufacture a cause to have one.

6. VERDICT + HAND-OFF — STOP at the Iron Law. Emit NO fix. Report the READING LIST (so a skipped read is visible), the confirmed cause + repro, the killed candidates, and "M#### now carries a PROVEN root cause + $0 repro → ready for /firmup." If it dead-ends at a surviving tie or a bare hypothesis, say so plainly and name the exact evidence still missing + what would settle it — do not dress a hypothesis as a diagnosis. ⭐ If the investigation keeps EXPANDING — each probe reveals new coupling in a different place, or a fix would need "massive refactoring" — that is the "three failed fixes → question the ARCHITECTURE" signal arriving early: STOP, surface "the design may be wrong," and discuss with me. Do not force a cause to close the turn.

⚠ RED FLAGS — any of these means STOP and return to the differential (step 2): "it's probably X, let me fix that" · proposing a fix before tracing the data flow · "quick fix now, investigate later" · "I understand it" with no repro to show · collapsing to one hypothesis at the START · editing the thing that FAILED because you have a tidy reason it's fine (that is quieting the disagreement, not resolving it). Simple bugs have root causes too; systematic is FASTER than guess-and-check.
