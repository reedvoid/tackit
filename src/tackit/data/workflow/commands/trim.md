Aggressively trim + consolidate MEMORY.md. This is the DESTRUCTIVE, global-view counterpart to the add-only /handoff.

⛔ SOLO ONLY. This command REWRITES MEMORY.md wholesale and DELETES content. If another session is active — or might run /handoff while this runs — STOP: a concurrent add-only handoff writes from its own stale copy and your rewrite would clobber it (and vice-versa). Confirm you are the only active session before proceeding — with THE SOLO CHECK in `~/.claude/commands/handoff.md` step 4 (`ListAgents`, then re-checks ~60 s apart: a peer listed right after a git commit is usually the security-guidance plugin's commit reviewer, gone within ~3 minutes; only a peer still listed after the re-checks is a concurrent session). This is the ONE place a full MEMORY.md rewrite is legitimate, precisely because nothing else is writing.

WHEN TO RUN — two triggers, SAME mechanics (both solo, both rebuild the file):
- (a) BLOAT-GC: the /handoff bloat alert fired. The file is EXTREMELY bloated — cut HARD; shaving a few lines is pointless.
- (b) ONE-TIME MIGRATION: MEMORY.md is still in an OLD format (inline prose, no clean two-zone split — e.g. the pre-restructure file). Convert it into the target shape below. Here the priority is LOSSLESS RELOCATION (move every inline block into a topic file + establish the two zones), deleting only what is genuinely stale / already-captured. Getting the structure right matters more than cutting.

⭐ Either way, the goal is a lean INDEX, not a lightly-tidied essay. Default assumption: any inline prose block can move to a topic file and be replaced by a one-line pointer, and anything already captured in git + tackit + logs is a pointer (or gone), never prose.

⭐⭐ VERIFY AGAINST THE SOURCE — NEVER DECIDE STALENESS FROM THE MEMORY TEXT ALONE. FORCEFUL / load-bearing — the most important rule here.
- why: MEMORY.md is a STALE, LOSSY SUMMARY, not the authority. Judging what to keep/cut by re-reading it is CIRCULAR — it is how a task that tackit already closed keeps a live `⭐ NEXT` slot, a hub that is actually done reads as open, and a rule whose D# was superseded survives. The memory line's own prose CANNOT tell you its referent's real state; only the referent can. A failure is a disagreement, so consult the AUTHORITY: the memory text is never the authority.
- do: for EVERY keep / demote / delete / merge decision on an entry that NAMES a referent — a tackit task (`M#`/`T#`), a design/schema slice (`D#`/`S#`), a commit hash, a `[[topic-file]]`, a run-log — make the decision against that referent's ACTUAL CURRENT STATE, FETCHED THIS RUN, not against how fresh or stale the memory line reads:
  - tackit id → `show`/`board` it. `closed` / `wont_do` / `retired` ⇒ cut: the tracker holds it. `open` AND still the live priority ⇒ keep. ⭐ A `NEXT`/open-hub line whose task is terminal in tackit is STALE no matter how active its prose sounds — that mismatch is the exact bug this rule exists to catch.
  - `D#`/`S#` slice, commit, run-log, `[[topic-file]]` → OPEN it and confirm it still says what the entry claims BEFORE you compress, move, or drop the entry.
- don't-do: prune/demote/merge on the memory text's own say-so; assume "looks done" = done or "sounds active" = active; skip this check to save turns (skipping it IS the dangerous failure). If a referent cannot be fetched this run, do NOT delete on a guess — KEEP it and flag it in the report as unverified.

TARGET SHAPE — TWO ZONES, under one budget:

MEMORY.md BUDGET: Zone 1 (above the index heading) ≤ 40 lines and ≤ 8 KB; the whole file ≤ 120 lines and ≤ 12 KB; every Zone 2 line ≤ 300 bytes. Measure with `wc -lc`, not by eye.

Why bytes as well as lines: Claude Code loads only the first 200 lines or 25KB of MEMORY.md and drops the rest, and a file of few, very long lines passes any line count. A Zone 2 line over 300 bytes is prose in pointer form: move its detail to the topic file and keep a short hook.

MEMORY.md SHAPE: each NEXT item ≤ 250 bytes, each session's NEXT block ≤ 600 bytes, and the merged NEXT a trim produces ≤ 1.5 KB (ids, the next action, open user calls with their first-raised date; status, numbers and paths live in the task or a topic file; lower-priority ids go on one Parked line); RECENT SESSIONS keeps the newest 3, each hook ≤ 150 bytes; a Zone 2 bucket over 10 entries becomes one pointer to an index topic file.

- **ZONE 1 — ACTIVE CORE** (the top `# ⬅ ACTIVE` region; always-on, within the Zone 1 budget): ONLY what every cold session must hold WITHOUT a file read, in three sections:
  - `⭐ NEXT`: task ids + the next action + open user calls, within the SHAPE limits.
  - `## ⚠ HAZARDS`: one line per active hazard (something a cold session could do that would cause harm right now, e.g. a deploy that must wait). It overrides any general rule it contradicts, so it sits in Zone 1 where that rule is read.
  - DO-NOT-RE-DERIVE: ONE line each = the rule + a `[[file]]`/`D#` pointer to its detail, under an admission test: a line enters or stays only if no always-loaded CLAUDE.md, loaded command, the tracker skill or a design/schema slice already carries it, and current or next work needs it. A rule homed in a slice gets only its id (one line can list several slice ids). A line that fails the test goes to Zone 2 or is cut.
- **ZONE 2 — INDEX** (pure one-line pointers, ZERO inline content): RECENT SESSIONS, LIVE FACTS, FEEDBACK, REFERENCE, ARCHIVE. Every entry is `- [Title](file.md) — hook`. ARCHIVE is always one pointer to an archive index topic file; FEEDBACK and REFERENCE become one pointer to their own index topic file once over 10 entries; reuse an index file that already exists. One pointer per file: no Zone 2 line for a file Zone 1 already links. There is no DONE bucket: finished work lives in the tracker and the session files.

STEPS:
1. Read MEMORY.md IN FULL; record its size (lines and bytes, whole file and Zone 1, plus any Zone 2 line over 300 bytes) as the BEFORE.
2. For every inline prose block (durable invariants / methods / negatives / lessons, session narratives, hub-status tables): MOVE the detail into a topic file (create it, or confirm it already exists) and REPLACE the block in MEMORY.md with a one-line pointer. If the topic file already holds a long form of the same rule, the new text replaces the previous long form; never append another verbatim snapshot. Keep a load-bearing RULE as a Zone-1 one-liner ONLY if it is truly always-needed; else pointer-only in Zone 2.
3. MERGE the per-session `### [session: …]` sub-blocks under `⭐ NEXT` into ONE coherent NEXT priority. ⭐ FIRST verify each sub-block's task ids against tackit (per the VERIFY-AGAINST-THE-SOURCE rule): a sub-block whose tasks are all terminal does not belong in the merged NEXT at all — it is dropped. Merge only the entries whose referents tackit confirms are still open + live. If two sessions' *still-open* nexts genuinely conflict (not just concatenate), surface it and ASK rather than silently picking one.
4. DELETE ruthlessly — but EVERY deletion is JUSTIFIED BY THE SOURCE, never by the memory text (see the VERIFY-AGAINST-THE-SOURCE rule above; run the tackit/git/slice/file check FIRST for each entry you touch): stale / superseded / done-and-already-captured entries, confirmed terminal/stale AT THE SOURCE this run. Terminal/archived content is at most a pointer in the archive index, never prose. Also cut each DO-NOT-RE-DERIVE line that fails the admission test (name where the rule now lives), and move a FEEDBACK pointer whose rule was promoted into one of those homes to the archive index. A HAZARDS line goes only when the source shows the hazard is gone (e.g. the deploy happened). ⚠ Before deleting a fact that lives ONLY in MEMORY.md (no topic file, not in git/tackit/logs), MOVE it to a topic file first — trimming is RELOCATING detail + cutting what's already captured elsewhere, never LOSING a unique fact. An entry you could NOT verify at its source stays (flagged unverified), never cut on a guess.
5. Enforce every part of the budget, measured again with `wc -lc`. Zone 1 over → demote more to Zone 2 pointers. A Zone 2 line over 300 bytes → move its detail to its topic file and shorten the hook. Whole file over → move or cut more. Then enforce the SHAPE line: shorten each NEXT item, keep the merged NEXT within 1.5 KB (move lower-priority ids to the one Parked line), keep the newest 3 RECENT SESSIONS lines (older ones go to the archive index), and collapse any bucket over 10 entries into one pointer to its index file.
6. Report: BEFORE→AFTER size (lines and bytes, whole file and Zone 1), what moved to which files, what was deleted, and the merged NEXT. ⭐ For each entry pruned or demoted, name the SOURCE STATE that justified it (e.g. `M12 → closed in tackit`, `D34 → superseded by D56`), so the decision is auditable and not a bare "looked stale". List separately any entries KEPT-as-unverified because their referent could not be fetched this run.
